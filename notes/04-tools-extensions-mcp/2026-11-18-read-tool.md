# 2026-11-18：read Tool 的 offset 行号转换

文本内容拆成 `allLines` 后，`read` 根据可选的 `offset` 确定起始行：

```ts
const startLine = offset ? Math.max(0, offset - 1) : 0;
const startLineDisplay = startLine + 1;
if (startLine >= allLines.length) {
	throw new Error(`Offset ${offset} is beyond end of file (${allLines.length} lines total)`);
}
```

`offset` 是从 1 开始的人类行号，数组下标从 0 开始，所以代码减 1 得到 `startLine`。未提供 `offset` 时从下标 0，也就是第一行开始。`startLineDisplay` 再加 1，得到后续提示文字使用的行号。

**假设例子**：

```ts
allLines = ["第一行", "第二行", "第三行", "第四行"];
offset = 3;
```

此时 `startLine` 为 2，对应 `allLines[2]`，也就是第三行；`startLineDisplay` 为 3。如果 `offset = 6`，转换后的下标为 5，大于等于 `allLines.length`（4），代码就抛出越界错误。

下一步会用 `startLine` 和可选的 `limit`，从 `allLines` 中选出要读取的文本。

## 文本截断与首行超限

`truncateHead(selectedContent)` 检查选出的文本是否超过行数或字节限制。需要截断时，它按顺序逐行累计字节，保存放得下的完整行，遇到放不下的行就停止。

**假设例子**：字节限制为 50KB，三行分别为 10KB、20KB、30KB。前两行累计约 30KB；再加入第三行会超过 50KB，因此返回前两行并标记发生截断。实际计算还包含换行符的字节。

`firstLineExceedsLimit` 表示本次选出的第一行单独就超过字节限制。此时没有完整行可以返回，`read` 会生成提示，建议使用 bash 读取这一行的一部分。其他行放不下时，则走普通截断分支。

从 `const truncation = truncateHead(selectedContent)` 开始，本次读取的流程是：

```text
检查选出的文本是否超过行数或字节限制
→ 没超限：content 保存完整选中文本，truncated 为 false
→ 超限：truncated 为 true，content 保存能放下的完整行
→ 如果首行单独超出字节限制：content 为空，生成首行超限及 bash 读取提示
→ 其他截断情况：计算最后返回的行号和 nextOffset，追加继续读取的提示
```

**假设例子**：从第 3 行开始，本次只放下第 3、4 行，则 `endLineDisplay = 4`，`nextOffset = 5`。代码只生成 `offset=5` 的提示；如果模型之后再次调用 `read` 并传入 `offset=5`，新的调用才从第 5 行开始，并再次检查限制。

## 两种继续读取提示

两个分支都会提示下一次的 `offset`，原因不同：

- `truncation.truncated`：选中的文本超过工具的行数或字节限制，`truncateHead()` 截断了它。例如请求整个文件，但工具只返回前 100 行，提示从第 101 行继续。
- `userLimitedLines !== undefined && ...`：选中的文本没有被工具限制截断，但调用参数 `limit` 只选了部分行，文件后面仍有内容。例如文件有 10 行，传入 `limit = 2`，返回第 1、2 行，提示还剩 8 行，可从第 3 行继续。

这些数字是假设例子。如果选中的 `limit` 范围本身也超过工具限制，会先进入 `truncation.truncated` 分支。

## signal 与读取期间的取消

`signal` 是上层传入的取消信号对象；它存在并不意味着已经取消。`aborted` 是本次读取自己保存的标记，初始为 `false`。

```text
有 signal 时登记 onAbort 监听器
→ 上层对应的 AbortController 调用 abort()，signal 发出 abort 事件
→ onAbort 执行，将 aborted 设为 true，并以取消错误拒绝 Promise
→ 读取流程之后检查 aborted，已取消就退出，不交付成功结果
```

如果读取成功且没有取消，`aborted` 仍为 `false`。代码通过 `signal?.removeEventListener(...)` 在 signal 存在时移除监听器，再用 `resolve({ content, details })` 交付结果。这里的 `?.` 检查 signal 是否存在，并非判断是否取消。

## Extension、Hook 与 handler

- Extension 是一组扩展代码，可以注册处理函数来改变 Pi 的行为。
- Hook 是 Pi 提供的介入时机，例如工具调用前的 `tool_call`。它允许扩展返回结果，影响后续执行。
- handler 是扩展注册的函数；Pi 到达对应时机时调用它，由它检查事件并返回结果。

**假设例子**：扩展注册一个检查 bash 命令的 `tool_call` handler。Pi 将调用事件交给它；如果它返回带 `block` 的结果，Pi 根据结果阻止工具调用。

```text
Pi 到达工具调用前的介入时机
→ 调用扩展注册的 handler(event, ctx)
→ handler 检查并返回结果
→ Pi 根据结果决定是否阻止
```

Agent Loop 的 `beforeToolCall` 通过 `AgentSession._beforeToolCall()` 连接到 `ExtensionRunner.emitToolCall()`：

```text
模型请求 read
→ Pi 查找 read 工具
→ 预处理并校验参数
→ beforeToolCall 执行前 Hook
→ AgentSession 把请求交给扩展检查
→ ExtensionRunner.emitToolCall()
→ 扩展返回是否阻止
→ 不阻止：之后执行 read
→ 阻止：直接返回错误，不执行 read
```

多个 handler 依次检查；`block: true` 表示阻止，立即返回且不再调用后续 handler。一个 handler 未阻止时，后面的 handler 仍可阻止。

扩展通过注册处理函数，告诉 Pi 在哪个事件发生时调用它：

- `pi.on("tool_call", handler)`：工具执行前检查调用，可以返回 `block: true` 阻止执行。
- `pi.on("tool_result", handler)`：工具执行后处理结果，可以检查或修改工具结果。

同一个扩展如果前后都要处理，就分别注册处理函数。`hasHandlers("tool_call")` 检查当前有没有扩展注册执行前的处理函数；没有就跳过扩展检查。

`const runner = this._extensionRunner` 拿到的是扩展运行器，而不是某一个扩展函数。它管理当前加载的扩展，后面从中查找注册的处理函数。

**假设例子**：两个扩展都注册了 `tool_result`：

```text
runner 管理的扩展
├─ 扩展 A 的 tool_result 函数
└─ 扩展 B 的 tool_result 函数
```

`runner.hasHandlers("tool_result")` 检查是否至少有一个对应的处理函数；有的话交给 `emitToolResult()` 处理。
